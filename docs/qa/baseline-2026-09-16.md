## 5. Portões de verificação (comandos canônicos)

### 5.1 Testes do backend — **rodam no host, não no container**

```bash
cd "C:/Projetos TI/moriah_app/backend"
pip install -r requirements-dev.txt      # só pytest + pytest-django
python -m pytest -q
```

**Resultado no baseline: `67 passed, 3 warnings in 1.99s`.**

`pytest.ini` já aponta `DJANGO_SETTINGS_MODULE=config.settings_test`, e `config/settings_test.py`
usa **SQLite `:memory:`** com `MEDIA_ROOT` temporário — ou seja, a suíte **não toca o Postgres de
desenvolvimento** e não precisa do Docker no ar.

> **Armadilha registrada (Fase 0):** o container `moriah_app-backend-1` **não tem pytest
> instalado** (a imagem usa `requirements.txt`, sem as dependências de `requirements-dev.txt`).
> Rodar `pytest` dentro do container falha; `manage.py test` também não serve porque os módulos de
> teste importam `pytest` (14 arquivos usam fixtures/`pytest.mark`). **O caminho oficial é o host.**
> Se a intenção for rodar a suíte em CI/container, é preciso acrescentar as dependências de dev à
> imagem de testes — registrar como item de infraestrutura, não como bug do app.

## 7. Reprodução de uma sessão de QA

1. `docker compose up -d` e confirmar `docker ps` (§2).
2. `python manage.py seed_mvp` no container (idempotente — pode repetir sem duplicar).
3. Registrar `git rev-parse --short HEAD` (tem de ser `40ebc25` ou um commit posterior anotado).
4. Rodar os portões: `pytest -q` (host) e `tsc --noEmit` (`mobile/`) — §5.
5. Abrir o app em `http://localhost:8081`, autenticar com a conta do papel em teste.
6. Para cada fluxo: registrar papel, viewport (`desktop` ≥1024px / `mobile` ≤480px), estado
   inicial, ação, resultado e evidência (screenshot + comando).
7. Testes que **escrevem** (enviar contribuição, criar escala, responder escala, revisar
   contribuição) devem ser feitos em banco isolado **ou** seguidos de re-seed registrado.
   A suíte automatizada é a via segura: ela usa SQLite em memória.

## 8. Limitações conhecidas deste baseline

- Não há verificação de ponta a ponta dos papéis `secretary`, `coordinator` e `pastor` (§6.1).
- Não há cobertura de QA do app em **viewport mobile nativo** (só web, 8081) — a diferença entre
  `Screen.tsx` (sidebar desktop) e as tabs mobile não tem evidência de dispositivo real.
- `PersonalCommitment` e `MemberUpdateRequest` vazios significam que os fluxos de agenda pessoal e
  pedido cadastral só foram exercitados em criação, não em listagem com dados.
- O endpoint de revisão de contribuição aceita qualquer transição de status (§4.1 de
  `docs/fase-0-decisoes-2026-09-16.md`): **não usar o app para "testar" re-decisão sem saber que o
  backend vai aceitar.**
